## 发布版与本机版

GitHub Releases 提供发布版：请求额度固定为每分钟 40、每小时 100、北京时间每日 1000 次，间隔固定为 2000 毫秒。每天在北京时间 02:00–03:00、14:00–15:00 两个窗口内各随机同步一次；每个安装实例按天生成随机时间，重启不会重新抽取。错过窗口不补跑。每轮调取结束后，手动调取冷却 30 分钟，重启或更换浏览器不会清除冷却，进行中的请求不重复排队。固定策略在后台执行，界面和设置接口不能覆盖。

发布版继续使用官方源，BATrace 选项冻结；本机版保留可调额度与间隔、原有白天/晚间调度，以及官方/BATrace 数据源选择。本机版不施加发布版新增的固定策略和 30 分钟冷却。两种构建不修改彼此的数据库设置。

Windows 构建默认生成发布版：`powershell -File scripts/build-desktop.ps1 -Edition release`。开发用本机版使用 `-Edition local`，应单独保存，不上传为公开下载包。

面向 Broken Arrow 朋友开黑的可视化战绩与长期数据管理工具。后台在本机持续采集，将已获取的对局归档到本地 SQLite 数据库，逐步积累更久远的记录，支持长期查看和分析；首次可回溯的范围仍受上游数据可用性限制。每人可登记多个游戏账号，默认统计至少三位不同朋友实际参战的对局；朋友也可通过独立的公开只读网站查看已发布的分析。

| --- | --- | --- |
| 只在本机使用 | 自己管理、分析，不公开资料 | 本机后台负责采集 |

## Windows EXE 桌面管理器

在 [GitHub Releases 下载最新版 Windows 一键部署程序](https://github.com/sisi4376/broken-arrow-court/releases/latest)。下载 `BrokenArrowCourt.exe`；完整源码可从同一发布页的 Source code 下载。

Windows 10 / 11 x64 可双击 **`BrokenArrowCourt.exe`**，不用打开终端。EXE 内置完整程序和 Node.js 24 运行时，采用 Windows 自带的 .NET Framework WinForms 界面；不是把 `.ps1` 改名为 `.exe`。构建产物不含真实 `.env`、数据库、备份、生成站点、Git 元数据或任何登录凭据。

### 当前这台电脑怎么用

正式入口只保留项目根目录的 **`BrokenArrowCourt.exe`**。它是桌面管理器，实际后台是同目录的 `src/server.mjs`，本机管理地址为 `http://127.0.0.1:4317`；`site/` 和线上 Pages 是公开只读网页，不是另一套后台。请保留整个项目目录，不要把 `data/`、`.desktop/`、`src/` 或 `site/` 当成旧版本删除。

1. 将 EXE 保留在现有完整项目根目录，双击启动。会自动使用该目录的 `.env` 和数据库，**不会清空或复制你的历史数据**。
2. “后台与状态”中可启动、停止、重启后台，打开管理页、只读预览或线上网站，检查 Git / GitHub CLI / 登录 / Pages 状态。
3. 已经部署过时，在“网页发布”直接点击 **立即更新网页**，无需再次勾选同意或重复确认。更新始终使用已经配置的发布仓库，不会因输入框中尚未保存的地址而切换目标；未配置发布仓库时仍会要求先完成首次部署。首次部署保留公开数据确认。过程会自动切到“运行日志”，显示进度、错误与结果，不再窗口闪退。
4. 首次部署时填写 `用户名/仓库`，需要时勾选“创建公开仓库”，再点击 **一键部署 Pages**。仍会拒绝不相关的非空仓库、不同远程地址或擅自公开私有仓库。
5. 每轮采集结束后，有公开数据变化就自动更新网页，不受推送间隔限制；没有变化则不重复提交。手动导入、改名、账号归属和专精更正等公开数据变化也会立即检查发布；窗口中的“其他更改推送间隔”仅合并界面代码等文件变化，保存后重启后台生效。点击最小化或右上角关闭会收起到右下角托盘，后台继续运行；单击、双击托盘图标或右键选择“显示管理器”恢复窗口。再次双击同项目的 EXE 也会唤出已有窗口，不重复启动隐藏管理器。右键菜单可打开本机管理页、启动或停止后台，选择“退出管理器（后台继续运行）”才真正退出窗口程序；正在执行操作时可收起，操作结束后可退出。日志保存在项目的 `.desktop/manager.log`。

管理器在托盘时，操作失败仅发送托盘通知并保存完整日志，不弹出挡住隐藏窗口的模态对话框。重新打开窗口会自动定位到失败日志；前台错误弹窗只展示短摘要，避免长堆栈撑出屏幕。重复启动后若旧窗口长时间无响应，会给出明确提示而不是继续创建进程。管理器窗口与采集后台是两个独立进程，退出管理器不会主动停止采集；开机或重启 Windows 后仍需启动后台，或按下文安装开机启动任务。

### 拷到另一台电脑怎么用

- 可以只拷贝这一个 EXE。若旁边没有完整项目，首次运行会在 `%LOCALAPPDATA%\BrokenArrowCourt\application` 释放程序，并使用那里独立的 `.env` / 数据库。也可在窗口选择一个新的空目录安装，或选择已有完整项目。**移动 EXE 不会自动迁移原电脑的历史、朋友或 GitHub 登录状态。**
- 新电脑不必单独安装 Node.js；内置运行时释放到所选项目的 `.desktop/runtime/`。原始数据库仍只在该项目的数据目录保存，不会写回 EXE。
- 发布需要该电脑有 Git 和 GitHub CLI。缺少时使用窗口中的官方下载入口安装，然后点击“检查环境与部署”。“登录 GitHub”会打开本人操作的 CLI / 浏览器授权窗口，程序不保存密码或打包 Token。
- 新项目启动后台后需在浏览器创建管理员和朋友名单。若要沿用历史，先按备份章节恢复数据库；没有恢复的独立安装不会凭空出现旧数据。
- EXE 当前没有购买代码签名证书，Windows 可能显示未知发布者。请核对文件来源；不要关闭防病毒软件或绕过系统安全拦截。如被拦截，应保留报错再排查。

EXE 支持一键 GitHub Pages 配置和静态仓库推送，不会代替 Cloudflare 的首次账号授权。已经连接同一 Git 仓库的 Cloudflare Pages 会随新提交更新。推送完成后还需等待云端构建；“检查环境与部署”可以读取 Pages 当前状态。

### 从源码重新构建 EXE

完整项目下运行（需要 Windows、x64 Node.js 24+ 和系统 .NET Framework C# 编译器，不需要 Electron/npm 依赖）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build-desktop.ps1
```

输出为根目录 `BrokenArrowCourt.exe`，构建清单及中间文件在 `.cache/desktop-build/`。白名单打包公开程序文件，并对每个包内文件记录 SHA-256；不打包 `data/`、`.env`、`site/`、`.git/`、`.cache/`、`.desktop/`。重建前先关闭运行中的管理器。已有完整项目会使用原目录源码，不会用内置包悄悄覆盖本地修改。

打包的 Node.js 许可见 `desktop/NODE-LICENSE.txt`；sql.js 和 Lucide 的许可随程序保留。桌面状态层有独立单元测试；EXE 的 `--self-test 输出目录` 会在全新测试目录解包、启动/停止空后台并生成常规/紧凑窗口截图，不应使用正式数据目录作为测试输出目录。

## 本机启动与首次配置

### 群友在公开网页请求更新（可选）

公开网页支持“请求更新”按钮：群友无需登录，成功传递到本机队列的请求逐个执行一次增量同步，随后检查并提交网页发布。运行期间每 15 秒检查队列。它不打开本机公网端口，不上传私人数据库。支持以下两种中转方式，单独部署静态网页不会启用它。

本机版的群友请求采用**全站共享 10 分钟冷却**，从一次任务开始计时，同时最多执行一轮。冷却期间的其他请求返回冷却提示，不继续堆积采集任务；窗口内即使本次任务失败也不立即重跑。冷却时间保存在本机数据库，重启后台或更换浏览器不会绕过；网络回执重试不占用新窗口。网页收到结果后显示剩余冷却时间。本机版管理员原有手动同步和自动同步设置不受这项群友请求限制影响。发布版的管理员与群友调取共用每轮结束后 30 分钟冷却，不能通过更换入口绕过。

采集是增量的，网页导出仍会重建公开数据库及统计快照；Git 只提交和传输变化内容，未改变的内容文件可复用。手动发布会先比较数据与源码指纹，有变化时只生成一次快照，无变化时跳过计算，不再先完整导出一次后在发布阶段重复导出。源码指纹也包含导出器自身，更新投影逻辑后仍会重新生成。后台运行时，EXE 和发布脚本通过本机服务令牌将发布交给后台排队，等待采集结束，不再单独打开第二个数据库写入进程；后台停止时才使用独立发布流程。更新代码后应先重启后台，再使用新版发布命令。GitHub Pages 接到提交后的云端部署仍需要额外时间。

**无需额外账号的 ntfy 方式（当前选用）：** 在已有 `.env` 追加 `UPDATE_NTFY_URL=https://ntfy.sh`、`UPDATE_NTFY_TOPIC=court-updates-32位随机小写十六进制字符`；可用 `node -e "console.log('court-updates-'+require('crypto').randomBytes(16).toString('hex'))"` 生成主题。重启后台，再更新网页，即可显示按钮。有 ntfy 主题时优先使用此方式，无需部署 Cloudflare，也无需群友登录 GitHub。

云端默认仅缓存 **12 小时**（[官方说明](https://docs.ntfy.sh/publish/#message-caching)）。电脑持续离线超过缓存期限时请求可能丢失；后台取回的整批请求先存到本机数据库，已落地的队列不再依赖云端缓存。网页区分“已发送到中转服务”和“同步及发布提交完成”；12 小时未收到结果时提示未确认完成，允许重新请求。服务不可达或限流时显示失败。此方式受第三方服务可用性、地域网络和发布配额限制，不能保证所有群友网络都可访问。

主题只是随机路由标识，会随网页公开，不是密码；中转仅包含随机请求编号及完成状态。匿名公共主题不能验证请求者或回执身份，知道主题的人可以订阅、发送或伪造消息，不要通过它传输账号、对局或凭据。后台依然保留原有上游额度和限流。仅让一台电脑处理同一主题；重复传递同一编号不会再拉取。

**自建 Cloudflare Worker + D1 方式（可选）：** 可获得不依赖 12 小时缓存的持久队列。不要设置 ntfy 主题，再按以下步骤配置。

部署步骤（需要本人 Cloudflare 账号及 Node.js/npm；命令在 `relay/` 目录执行）：

1. 运行 `npx wrangler login` 完成本人登录，再运行 `npx wrangler d1 create court-update-requests` 创建队列数据库。将返回的数据库 ID 填入 `wrangler.toml` 的 `database_id`。
2. 将 `SITE_ORIGIN` 改为公开网页的准确来源，例如 `https://用户名.github.io`；不要包含仓库路径。浏览器按钮仅允许这个来源访问。
3. 运行 `npx wrangler d1 execute court-update-requests --remote --file=schema.sql` 建表。
4. 用密码管理器生成至少 32 位随机密钥；运行 `npx wrangler secret put CONSUMER_TOKEN` 输入密钥，再运行 `npx wrangler deploy`。密钥只保存在云端秘密配置和本机 `.env`，不要发到聊天或公开仓库。官方操作参考：[D1 创建与绑定](https://developers.cloudflare.com/d1/get-started/)、[Worker 密钥](https://developers.cloudflare.com/workers/configuration/secrets/)。
5. 在本项目已有 `.env` **追加** `UPDATE_RELAY_URL=https://实际服务地址.workers.dev` 和 `UPDATE_RELAY_TOKEN=同一密钥`，保留已有配置。重启本机后台，再用管理器“立即更新网页”发布一次。按钮仅在配置服务地址后显示。

仅让一台电脑消费同一队列。每个请求编号与本地同步记录一起持久保存；网络错误只重试回执，不重复采集。中途重启打断的任务会报告未完成，群友可重新请求；不承诺断电中的任务必然成功。关闭自动同步时，群友请求仍属于单次手动任务，不会重新开启自动同步。请求遵守既有账号静默、重试间隔、额度和上游限流；“同步完成”不保证上游已经提供刚结束的对局。

成功提示表示采集和发布提交完成，线上 Pages 构建仍可能需要时间。同步有错误、后台中断或发布失败时，按钮提示未完整完成，本机日志记录详情。自建 Cloudflare 方式默认同一公网 IP 每分钟一次、全站每天 100 次、最多 20 个待处理请求；达到限制时明确拒绝，不把请求合并成一轮。共用网络的群友共用该 IP 冷却。网站来源限制不是身份验证；当前适用于小群使用，公开推广前应另加验证。自建队列已完成回执保留 30 天，待处理请求不会定期清空；上述限制不代表 ntfy 公共服务的配额。

### 1. 准备完整项目与运行环境

- 获取完整项目目录，确认包含 `src/server.mjs`、`scripts/`、`public/`、`readonly/`、`vendor/`、`Start.ps1`。**只读发布仓库只有生成的网站文件，不能拿来运行采集后台。**
- 安装 [Node.js 24 或更新版本](https://nodejs.org/)。在终端运行 `node --version` 确认版本；安装后可能需要重新打开终端。
- 仅运行本机程序不需要 Git、GitHub CLI、npm 或 `npm install`。公开部署另外需要 [Git](https://git-scm.com/downloads) 和 [GitHub CLI](https://cli.github.com/)。
- 下文所有命令均在完整项目根目录执行，不是在 `site/` 内执行。Windows 启动脚本也支持本机已有的 Codex 捆绑 Node.js，但换电脑后应独立安装 Node.js。

### 2. 启动与创建管理员

Windows PowerShell：

```powershell
powershell -ExecutionPolicy Bypass -File .\Start.ps1
```

首次打开创建管理员，没有预置密码。默认地址 `http://127.0.0.1:4317`，端口被占用时自动选择下一个。`Start.ps1` 会显示并打开实际地址。

macOS / Linux 或需要查看终端日志时，前台运行：

```sh
node --env-file-if-exists=.env src/server.mjs
```

前台进程退出后不再采集；Linux 长期运行可使用自己的进程管理器，并固定工作目录为项目根目录。项目没有预置 Docker 或 systemd 一键安装器。

### 3. 配置朋友与首次同步

1. 在首次打开的页面创建管理员，没有默认密码。
2. 在“看守所”添加朋友，登记各自的游戏账号；至少登记三位不同朋友才能产生符合口径的开黑统计。
3. 在“书记官室”启动同步，等待汇总、详情和涉及单位资料逐步归档。上游有请求限速，首次回溯可能较慢。管理员也可在本地总览或书记官室页，点击“立即同步”旁的“更新网页”，直接发布当前已归档数据，无需重复确认；如果正在采集则排队至采集结束，状态会显示发布中、提交时间或错误。此按钮不会抓取新对局，也不在公开只读站显示，尚未配置仓库时需先在 EXE 完成部署。
4. 打开 `http://127.0.0.1:4317/readonly/` 检查公开预览。实际端口以启动输出为准，后台每分钟检查一次是否需要生成快照。
5. 公开前确认朋友同意公开称呼、游戏账号关联与对局数据，详见后面的隐私边界。

### 停止与状态检查

```powershell
powershell -ExecutionPolicy Bypass -File .\Stop.ps1
```

服务状态：`node scripts/service.mjs status`。

配置文件修改后要停止再启动，单独再运行一次 `Start.ps1` 只会复用已运行的服务，不会加载新配置。首次使用可在文件不存在时复制 `.env.example` 为 `.env`；**已有 `.env` 不要覆盖**。

## 建立朋友名单

1. 管理员在“看守所”添加真实的朋友，每个人只建一份朋友记录。
2. 每位朋友可以登记多个游戏账号。当前支持游戏数字 ID、Steam64 ID、Steam 主页或 BATrace 玩家链接解析；昵称搜索暂不可用，也可以直接登记游戏内数字 ID。
3. 用朋友行上的邀请按钮生成邀请码，朋友注册后会认领已有记录，不会多生成一个人。全局“邀请注册”会新增一位朋友。
4. 管理员可以调整游戏账号归属，朋友可以管理自己的账号。账号全局唯一，避免同一个账号被计入两个人。

登记仅建立分析归属，不验证 Steam 账号所有权。本站登录账号和游戏账号是两种不同的账号。

## 开黑口径

人数筛选默认为“同局 ≥ 3 人”，也可选择“同队 ≥ 3 人”或“所有比赛”。“所有比赛”纳入已登记且启用朋友的全部已归档参战对局，包括单人、双人和多人对局，并应用于总览、卷宗和分析；日期、地图、模式及朋友筛选仍有效。首次打开及清除筛选后恢复“同局 ≥ 3 人”。公开只读版在已发布档案范围内使用相同筛选。

总览、对局档案和庭审分析默认筛选“普通模式”，可切换“全部模式”查看其他模式；清除筛选时恢复普通模式。BATrace 和官方战报省略的 `Type=0` 均按普通模式识别，`Type=1` 显示为自定义，`Type=3` 显示为遭遇战。旧官方误标记录依据原始响应自动修正，真正未知来源的模式不强行归类。

- 同一局至少 **3 位不同的启用朋友**实际参战，才纳入法庭统计。
- 同一人的多个游戏账号，人数只计一位。
- 按用户要求，朋友分处两边也属于同一局开黑；“同队至少三人”是额外筛选，不是默认口径。
- TeamId 100 的观战者不计入参战朋友。
- 归属调整、停用或恢复后，历史记录立即重算。
- 同一人多账号参与一局时，成员局数只计一次，分数相加；如果两边都有其账号，该成员该局胜负记为未知。
- 分数交换比是摧毁分 / 损失分，和单位数量 K/D 分开。
- 朋友表现中的摧毁分、损失分、占点和友伤均为场均值。同一朋友同局多账号先合并再平均；友伤仅以详情完整的场次作为分母，缺失详情不记为零，并显示样本局数。评分变化仍为累计变化，单场详情仍显示该局实际值。
- 生涯统计明确独立展示，包含单排，不会混入法庭的三人开黑统计。

### 战斗、经济与补给分析

- 总览和“庭审分析 → 朋友表现”均可切换战斗、经济、补给。经济显示场均出场分数、退款分数、击毁 / 损失数量和经验；补给显示场均消耗补给、补给队友、从队友补给。单场详情仍显示该局实际值。
- “庭审分析 → 蘸饭罪名榜”在同队搭档之前，判刑榜与减刑榜左右并列（小屏上下展示）。判刑榜包括小馋猫罪（场均消耗队友补给降序）、KD失职罪（分数交换比升序）、击杀摸鱼罪（场均击杀分升序，使用 DestructionScore）、白给浪费罪（场均损失分降序）、胜率拖堂罪（已知结果胜率升序）、占点旷工罪（场均占点升序）。减刑榜为运输大队长（场均补给队友降序）与**重防赎罪榜**（场均重防击杀数降序，替换原部署次数榜）。各项有独立有效样本数，共用可调最低局数门槛；相同值并列。KD失职罪采用与被告表现一致的累计摧毁分 / 累计损失分，不取逐局比率的平均值，也不再按单位数量排名；有分数记录的摘要局也参与，最低局数使用有效分数记录数。0 / 0 不排名，无损失分但有摧毁分显示 ∞。罪名榜不改动刑期计算。

需要暂停抓取时，可在本地书记官室关闭自动同步。该设置持久保存在数据库，重启后台或 EXE 不会自动恢复；暂停期间现有档案、查询、离线重新统计、网页发布和备份仍可使用。点击“立即同步 / 调取新卷宗”或“全量回溯 / 重查旧案”仅执行本次手动任务，保持自动同步开关的原有状态；关闭自动同步时仍可手动执行及排队，关闭开关只暂停自动采集，不中断手动任务；不希望访问 BATrace 时也不要手动运行补抓、玩家搜索或联网更新目录工具。
- 重防赎罪榜统计**每人自己的重防取得的击杀**：按单位目录 `role=15` 识别全部型号，累计这些单位的 `KilledCount`，再除以有效单位详情局数。未出重防的有效对局也计入分母，完整 protobuf 省略的零击杀按零处理。同一朋友多账号先按人、按局合并；同局重复部署、阵亡或退款前已取得的击杀均保留。表内显示累计击杀，可展开每个型号的击杀与部署次数；部署次数仅作核对，不参与排名。
- 重防击杀只使用完整详情。该朋友同局任一单位目录分类缺失，或击杀数非法，该朋友这一局从重防项整体排除，避免未知分类被误算为没有重防；页面展示排除数量，无有效记录显示未知而非零。服务器与公开只读版使用同一逻辑，不需要重爬完整对局。
- 该数据**不代表击毁敌方重防的数量，也不保证全部目标都是飞机**。现有源记录有各单位的总击杀数，但没有完整的“击杀者—目标”对应关系。
- 减刑榜另有 **空优立功榜**：统计每人以实际空战挂载出场的固定翼飞机所取得的 `KilledCount`，按有效局数的场均值降序，显示两位小数、累计击杀、排除局数，可展开型号、挂载名称与原始 `OptionIds`。同一朋友多账号合并，每局只算一个样本；阵亡/退款前战果保留，未出空优机的有效局也计入分母。遵从同一最低有效局数与日期、地图、模式筛选，不修改刑期模型。
- 空优挂载识别版本 `air-superiority-v1`：仅目录角色 160–164 的固定翼候选机，按每次部署实际保存的 `OptionIds` 选择各修改槽，解析选中挂载炮塔及不可替换的基础武器。必须携带有弹药的空空导弹（武器类型 87 / 88），只允许额外携带机炮（116）；油箱、电子干扰等无攻击武器的选项可保留。炸弹、火箭、反辐射、对地导弹或混合挂载不入榜，直升机和无人机不作为候选。不是凭飞机名称、飞机总出场数或 `role=164` 直接算空优。
- 不补默认挂载：缺少槽选择、未知选项、同槽冲突、替换机体未确认、武器资料不全或非法击杀数时，该朋友该局整体从空优项排除；有明确对地武器的挂载可直接排除，不需要猜测其他未知选项。缺失值不是零，机炮也可能打击地面，因此**空优机总击杀仍不等于击落敌机数量**。历史挂载无法被当前目录确认时保留原始记录并显示排除，不臆造匹配。
- 飞机挂载目录归档在 `analysis_catalogue.air_superiority_model`，完整目录原响应也保存在源快照；程序增量同步时补齐新机型并每 7 天刷新一次，使用数据源当前数据库版本。失败后保留已有目录并冷却至少 1 小时，遵守上游限流。管理员可运行 `node scripts/update-air-catalogue.mjs --force` 手动刷新。公开版携带相同的规则、归一化目录与白名单 `OptionIds`，离线可算；挂载目录变化也会触发重新导出，部署方式与其他网页更新相同。
- 补给和经济仅用详情完整的合格对局计算。同一朋友同局多个账号先相加，再按朋友的有效局数平均；缺失详情不记为零，完整 protobuf 详情省略的零值按零计算。队友指所有同队玩家，不仅是登记的朋友；上游没有逐人补给流向，不能据此判断具体是谁补给了谁。
- 补给榜默认至少 5 局完整详情，可调整“补给榜最低完整局数”；“同队搭档”默认至少 5 局共同同队对局，可调整“同队搭档最低局数”。两项门槛各自独立，均遵从当前日期、模式、地图等筛选；胜率仍以已知结果为分母。
- 已归档完整详情会直接参与新统计，无需重新抓取或迁移数据库。公开只读站点使用相同计算逻辑，更新源码后重新导出 / 发布即可。

### 个人其他对局

个人档案的“法庭对局”和“其他对局”分页列出已同步的比赛，同一朋友多个账号参与同一局只列一次。其他对局指未达到三位登记朋友参与条件的比赛，可按日期、地图、模式筛选；默认仍为普通模式，不影响刑期、胜率榜、庭审分析等法庭统计。账号历史受上游可查询范围限制，不保证拥有自账号创建以来的全部比赛。

公开网页现已获授权包含活跃登记朋友参与的其他对局，仍不导出没有登记朋友参与的无关记录、密码、会话、私人配置或原始源快照。公开版只能查看，补抓与账号管理仍在本地进行。常规对局档案和所有法庭榜单默认仍只展示三人合格局。

后台优先补抓合格法庭对局，每轮最多补齐 50 场详情，其中个人其他对局最多 10 场，个人详情请求至少间隔 5 秒。尚未取得完整战报时显示“已存摘要”，遇到限流进入冷却、失败保留记录并自动重试；管理员也可在该局详情中安排补抓。个人比赛详情与其他完整战报一样持久存储，后续发布自动携带最新可用详情。

### 单场玩家详情

单场“团队战绩”中点击任意玩家姓名，即可查看该账号的本局详情；未登记队友、对手与登记朋友都支持。朋友称呼另有个人档案入口。弹窗内可切换本局玩家，查看击毁/损失数量、分数交换比、评分变化、战斗/友伤、经济、三项补给与经验数据，以及原始字段。这里只看单场账号数据，不把同一朋友的其他账号或其他比赛混入。

单位按侦察、步兵、载具、支援、直升机、固定翼分列；飞行员与未知分类单独保留。同型号的不同实际 `OptionIds` 分开汇总，部署数、总伤害和总击杀不混用；点击单位可查看实例 NetID、出场/阵亡时间、退款状态、伤害/击杀/补给与原始挂载。未记录阵亡不等于确认存活，目录基价不是历史实际挂载价格。缺失详情或显式未知显示“—”，完整 protobuf 的省略标量零才按零显示。

阵亡数包括有正数 `DeathTime` 的实例，以及战报明确标记 `SelfDestruction=true` 的自毁实例，每次部署只计一次，退款不计阵亡。兼容旧记录时，仅在自毁标记缺省、没有正数阵亡时间且 `TotalSelfDamageDealt` 恰为数值 `-1` 时采用自毁哨兵规则；这是归档兼容规则，不是根据普通自伤推断死亡。显式 `false` 或异常标记不适用该规则。自毁可能没有阵亡时间：实例状态显示“自毁 / 坠毁”，时间显示“未提供”，时间轴不会画成存活到结束；标记本身不能区分具体事故原因。公开单场档案和只读数据库保留相同证据，不改写赛后损失分或刑期算法。

罪名榜“自毁长城罪”按本人场均自毁损失分降序排名：逐次部署确认自毁兵牌，按该场比赛起止时间对应版本目录及实际 `OptionIds` 计算完整挂载价值，同局合并本人多账号后求和，再除以有效计分局数；没有自毁的有效局也计入分母。单位数量仅作辅助，不再作为排名依据；这里是自毁兵牌的目录价值，不是整局 `LossesScore`，也不冒充无法取得的实际成交价。展开每场记录可查看兵牌详细名称、挂载、单价、账号、实例编号、击杀、伤害与出场/阵亡时间，缺失时间不推算。

确认包含明确标记的自毁或坠毁，不区分是否故意，不把普通阵亡或正数自伤纳入。每人每局先合并多账号，再逐个账号校验单位生命周期、阵亡记录与赛后损失数量，以及自毁标记类型；仅有“详情已抓取”不足以证明记录完整。缺失详情、旧版生命周期缺失、损失记录不齐或标记异常的对局列入待核实，不补零；价格未知、版本跨维护或有任一自毁兵牌的挂载不能完整计价时，该个人对局也整体排除场均计分，不借用当前价格或只计基价。累计确认数、已知分与逐局兵牌仍全部保留，部分已知分不混入场均分子；榜单下可查看待核实原因及未达最低局数的记录。公开快照只携带确认兵牌的白名单计价结果，默认预计算及自定义筛选与本地算法一致。沿用日期、地图、模式及三人开黑筛选，不修改蘸饭指数或刑期加减分。

自毁核查工具：`node scripts/audit-self-destruction.mjs` 默认离线检查全部归档、详情快照及单位索引，不修改数据库。需要修复时先停止本地后台，再运行 `node scripts/audit-self-destruction.mjs --apply --refresh=20`，可加 `--ids=9374015,其他对局ID` 优先核对指定比赛；`--refresh` 限制本轮回源数量。工具写入前自动备份，逐局低频请求，仅接收不丢失既有单位或自毁证据的更完整详情；遇限流、拒绝或连续失败停止，不以空响应覆盖旧数据。报告保存在本地 `.cache/self-destruction-audit/`，不会公开原始档案。旧战报回源后仍未提供的事件无法可靠重建，应保留“未知”，不要把自伤或未退款直接算成坠毁。完成后重新启动后台并更新网页。

单位卡片右上角突出显示分数，下方直接展示本局选择的挂载名称。可完整解析时展示目录基价 + 本局所选挂载增减分，不能确认时展示目录基价；参考价类型保留在悬停说明和单位明细中，不在兵牌上重复标注，不擅自补默认挂载。点进单位可看到挂载槽、名称、ID、逐项增减分和目录版本。价格采用当前版本目录，不保证等于历史对局当时的价格。

六类单位在桌面和手机始终并排显示，使用 144px 紧凑卡片；超出区域可左右滑动、用触控板横向滚动或按住鼠标拖动。拖动结束不会误打开单位详情，正常点击和键盘操作保留。

挂载目录保存在本地 `analysis_catalogue.unit_loadouts`，原始响应继续归档；增量同步自动补齐新单位，每 7 天检查一次，版本变化时重新获取。可手动运行 `node scripts/update-unit-loadouts.mjs`；`--force` 强制重新请求。可选 `--translations=中文游戏本地化JSON路径` 导入名称翻译，之后自动同步会沿用；没有翻译时显示目录原名。公开网页只导出本局已选挂载的白名单字段，不导出完整原始目录或翻译表。

遇到上游限流会保留已完成进度并冷却至少 1 小时；`node scripts/update-unit-loadouts.mjs --cached-only` 可在不联网的情况下先解析同版本的已有快照。不要通过反复强制刷新绕过限流。

历史战报另按实际选项 ID 匹配 Batrace 的公开稳定版目录，排除 PTE/测试目录。新增槽位不能套在旧对局上，也不会给缺失记录补默认挂载。历史目录保存为 `analysis_catalogue.unit_loadout_history`，可运行 `node scripts/update-unit-loadout-history.mjs` 补齐，或加 `--cached-only` 完全使用已归档快照。常规后台同步也会检查新增的未解析记录。

卡片及单位明细会区分当前参考价、旧版挂载参考价、游戏目录补录。若多个完整匹配版本的挂载定义相同、价格不同，只解析名称并提示价格歧义，不给出唯一含挂载总分。即使价格一致，也不代表已确认该场比赛的准确游戏版本或历史成交价。

F-15E 的选项 `3341` 在 Batrace 当前接口中缺失，通过 [BA-Units 的固定游戏数据提交](https://github.com/JohnJinHM/BA-Units/blob/00116fddace6bac6bd43f89ecef43b4e1f8f191a/output/tables/Options.json) 确认为单位 `287`、槽位 `307` 的机腹空挂载，增价 0。需要在新安装中复现这项补录，可先登录 GitHub CLI，再运行 `node scripts/import-game-loadout-source.mjs`。程序归档同一提交的单位、槽位、选项三张表，只补实际出现且单位/槽位关系完全一致的缺失选项；不会导入其他单位的相同编号，也不替换现有目录定义。可用 `--ref=完整提交SHA` 指定审核过的新提交，后台不会自动从 GitHub 拉取或改用测试数据。

`node scripts/audit-unit-loadouts.mjs` 以只读方式统计部署记录的解析覆盖率、历史/补录数量、价格歧义和仍未解析的具体 ID。公开版仅携带每局最终的白名单显示结果与诊断，不公开原始游戏数据表或整份历史目录。

v2仅将净蹭补给改为独立罚分：`S=max(从队友补给−补给队友,0)/max(自身消耗,从队友补给,1000)`，单局 `20×clip((S−0.35)/0.65)`。35%以内仍不罚，超过后线性增加，100%时20分；不再乘战斗不足程度，也不提前扣除占点、重防、空优等贡献。所有有效局（含0分局）等权平均，仍按10局先验向0收缩，最后与其他项统一相抵。高净依赖可能是队伍约定的集中保障，不能仅凭这一项认定搭便车。

补齐两项未独立覆盖的证据：净供给以 `20×max(供给−接收,0)/max(自身消耗,供给,1000)` 减刑；单位损耗以平滑单位K/D相对同队参考的缺口乘价值交换不足程度，再乘20加刑。K/D仅在单位与价值交换同时不足时触发，未知数量不作零；其与价值交换仍相关，属于需要回放检验的实验附加项。运输不能证明补给的战术价值，多项相关战果叠加也可能过度减刑。页面显示每项有效/缺失局数、原始单局依据和样本是否与正式版一致，不能把试算结果当成已验证的真实贡献评级。

当前默认 `zhanfan-v10-stacked`，排行榜和个人页使用同一结果。公开网页只显示现行刑期，已隐藏旧刑期、新旧对照和“案例复核”，只读数据接口也不再提供案例复核或历史对照。**案例复核只在本地后台显示**；历史算法及对照API保留在后台供开发复现，当前静态导出不包含复核计算模块。公开战绩仍可被自行分析，这不是对既有公开数据的隐私隔离。**这是朋友之间的自定义娱乐规则，不是官方实力评级或真实刑罚；尚未经过人工标签、预测或回放验证。** 不按朋友名单或名次拉伸，不强制当前榜尾得到90分。

#### 历史 v9：单项映射至−100～200，合计后截断

将原 v6 的0～100基础量尺进一步线性展开：`新基础单项=3×旧基础单项−100`。原0、25、50、75、100分别对应−100、−25、50、125、200；中性点仍为50。单局公式为 `P(x,y,b)=clamp(50-75×log2((x+b)/(y+b)),-100,200)`；缓冲后的4倍、2倍、相等、1/2、1/4比例对应上述五个锚点。双方均为零仍记中性50。

只调整战斗兑现、战损交换的量尺及下限/上限。占点/重防/实际纯空优信用仍取最有利一条，两项各减最多20，最低−100；核心按60%/40%合成，向50作10局先验收缩，保留所有负分及超100的核心。胜负±10、蹭补给0～+8、友伤0～+4及各自触发条件、样本收缩不变。**只有最终合计截断到0～100，不先对单项或单局核心截断。**

构造示例（非真实朋友数据）：战斗−100、交换200，核心为20而不是80。20场、80%胜率，每场两项200且没有额外处罚或信用，核心收缩150、胜负−4，合计146，最终截为100。原始战报不改写、不重抓、不迁移数据库，免刑线仍为25。少量样本仍收缩，但极端证据在新版可能更早达到高分，不能把最低局数当成判决准确性保证。

**现行无期线为75分**：75分对应240个月（20年），75分及以上显示无期徒刑。25分及以下仍免刑；中间刑期采用 `max(1,round(240×((指数−25)/50)^1.4))`，总月数封顶360，低于75分时最多239个月，防止四舍五入提前进入无期。评分不因这次量刑线调整变化，刑期、规则参照和权重扰动范围共用当前模型的量刑参数。历史v8及更早模型仍保留85分无期线，用于真实版本对照。

`expandedZhanfanAnalysis()` 和 `expandedZhanfanComparison()` 保留v9及v8/v9历史复现；`signedZhanfanAnalysis()` 和 `signedZhanfanComparison()` 保留v8及v7/v8。当前默认API返回v10，本地 `?court_compare=1` 返回v9/v10；公开站仍禁用历史对照。v10沿用 `score_breakdown.item_floor=-100`、`item_cap=200` 与裁剪前合计；页面范围随模型元数据更新，不提供访客修改规则的接口。

#### 历史 v8：单项映射至−50～150，合计后截断（不再默认使用）

`P(x,y,b)=clamp(50-50×log2((x+b)/(y+b)),-50,150)`。缓冲后本人/参考值为4倍、2倍、相等、1/2、1/4时，分别记−50、0、50、100、150。双方均为零仍为中性50。战斗内摧毁/伤害按60%/40%合成，分别参考同局其他同队真人人均值；交换比较本人摧毁与损失，缓冲仍为500/50。先合并同一人的多账号，不将敌方、AI或观战者作为同队参考。

#### 历史 v6：核心满尺度、附加修正（不再默认使用）

v5 把100分拆成五项，胜负和样本收缩会让正常胜率者的高分受到结构限制；而且没有补给/友伤罚分时少了15分。v6 **保留 v5 的单局比值量尺、原始证据、占点/重防/空优有限信用、后勤触发条件和取证规则**，只改汇总尺度与修正方式：

| 项目 | 范围 | 计算 |
| --- | --- | --- |
| 核心表现 | 0～100 | 减免后的战斗罚分×60% + 减免后的交换罚分×40% |
| 胜负修正 | −10～+10 | `20×((败局数+5)/(明确结果局数+10)-0.5)` |
| 蹭队友补给 | 0～+8 | v5 的单局蹭饭严重度均值，向0收缩后乘8 |
| 友伤修正 | 0～+4 | v5 的单局友伤严重度均值，向0收缩后乘4 |

先计算核心，向50作 `n/(n+10)` 收缩；然后加三个修正，最后裁剪到0～100。不把132作为总权重再次归一化，不要求额外负面行为凑齐才能高分。胜负仍有最多20分的差距，但不会占用核心满分；未知胜负修正0，不能当作败局。无记录待取证，低于5局不排名，少于20局为初步结果，不因先验给空档案判刑。

占点、重防、实际纯空优挂载的信用仍最多各减战斗/交换罚分20点，取最有利路径、不叠加；改用60/40核心后，核心最多因此减20分。补给仍要求净依赖超过35%且减免后的战斗罚分高于中性，不送补给不罚、不跨局抵账。原始战报不修改、不重抓、不迁移数据库。

**高分可达性必须通过有限样本测试，而不只是纸面满分：**

- 40场、50%胜率，每场减免后战斗和交换罚分均为100，没有蹭补给或友伤：核心收缩后90，胜负修正0，最终90。
- 100场、80%胜率，同样没有额外罚分：核心约95.45，胜负约−5.45，最终90。
- 5场同类极差表现、全败、没有额外罚分：最终70，不能因少量样本直接达到90。
- 长期优秀表现仍可当庭释放；裁剪前可能小于0或大于100，最终限制为0～100。**这些是构造测试，不是任何朋友的实际数据，也不证明评分准确。**

| 长期参照（缓冲后比例，无信用和额外罚分） | 指数 | 娱乐刑期 |
| --- | --- | --- |
| 双倍兑现与交换、60%胜率 | 23 | 当庭释放 |
| 参考产出、等价交换、50%胜率 | 50 | 5年10个月 |
| 半数兑现与交换、50%胜率 | 75 | 15年6个月 |
| 四分之一兑现与交换、50%胜率 | 100 | 无期 |
| 四分之一兑现与交换、80%胜率 | 94 | 无期 |

中性50不是免刑线。仍保留≤25免刑、85对应20年、20年及以上无期及原非线性刑期函数。显示“核心分 + 带正负号的修正 = 裁剪前合计”，修正标为分值而非百分比；权重扰动只对核心两项重新归一化，对三个修正单独调整幅度，不是置信区间。

API 的 `score_breakdown` 包含 `core`、三个 `adjustments`、`before_clamp` 和 `ceiling_without_extras`。最后一项仅固定局数/胜负，假定每场核心极差且没有补给/友伤罚分，是**反事实上界，不是本人分数或真实战术贡献**。当前成员可能都不到90；提高可达性不等于强行把某个人变成90。

`coreZhanfanAnalysis()` 与 `coreZhanfanComparison()` 保留上述 v6 和 v5/v6 历史复现；`independentZhanfanAnalysis()` 与 `independentZhanfanComparison()` 保留 v5 和 v4/v5。未完整记录的视野、守点、威慑、协同和牺牲继续作为误判风险保留。

#### 历史 v5：基础独立计分、后勤条件加刑（不再默认使用）

v4 的三项共用贡献缺口，造成多项罚分一起归零；v5 将**战斗兑现、战损交换独立计分**，只有额外蹭补给项保留条件门槛。先固定量尺及行为参照，再回算档案，不根据当前分数范围拉伸：

`P(x,y,b)=clamp(50-25×log2((x+b)/(y+b)),0,100)`。缓冲后的比例为 4 倍、2 倍、相等、1/2、1/4，分别记罚分 0、25、50、75、100；双零保留中性 50。账号先按人局合并，队友参考均值排除本人、敌方、AI 与观战者。

| 项目 | 权重 | 依据 |
| --- | --- | --- |
| 战斗兑现 | 35% | `0.6×P(本人摧毁,同队其他人均摧毁,500)+0.4×P(本人伤害,同队其他人均伤害,50)` |
| 战损交换 | 25% | `P(本人摧毁,本人损失,500)`，不再乘贡献不足系数 |
| 蹭队友补给 | 10% | 净依赖超过35%，且减刑后的战斗罚分高于50时，按依赖程度和战斗不足程度相乘 |
| 长期胜负 | 25% | 明确胜局0、败局100；未知不计输，独立按已知结果数收缩 |
| 友伤约束 | 5% | `100×clip(友伤/(伤害+友伤+50)/0.05)`，不推断故意 |

- 占点信用 `20×clip((本人占点-其他队友人均占点)/(其他队友人均占点+2))`。重防、实际纯空优挂载分别对比本人该类单位击杀与队友同类人均击杀，使用相同公式和缓冲2。选择三者最有利的一项，不叠加；各从战斗和交换罚分减最多20，不低于0。两项基础综合罚分合计最多减少12；战斗罚分下降还可能缓解额外补给罚分。出场不是贡献证明、总击杀不是敌机击落；该类任一同队人的分类未知时不用该类比较。
- 补给净消耗 `N=max(从队友补给-补给队友,0)`，比例 `S=N/max(自身消耗补给,从队友补给,1000)`，单局额外罚分 `100×clip((S-0.35)/0.65)×clip((减刑后战斗罚分-50)/50)`。不送不罚，赠送只抵扣同局净消耗，不能跨局抵账，不把补给与击杀价值混加。
- 基础战斗、交换和胜负向50收缩，补给和友伤向0收缩，样本权重 `n/(n+10)`；胜负独立使用明确结果的 `k` 局。无记录仍为待取证，不因先验给空档案判刑。默认至少5局上榜、少于20局为初步结果；缺详情、非法必要字段、队伍不明、无同队参考、无效时长、全队无可见活动的对局不评分。完整 protobuf 的省略标量零与显式未知仍区分处理。
- 原始加权罚分直接作为指数，无分布放大、内部名次映射或事后定向调参。**中性参照42.5不等于无罪**；25分免刑线对应下表优势参照，不再把“参考水平”误写成“没有任何罚分”。这些仅为固定娱乐政策参照，不是经验证的强弱分界。

| 长期参照（缓冲后的比例，无额外罚分/信用） | 指数 | 娱乐刑期 |
| --- | --- | --- |
| 战斗和交换均为2倍，60%胜率 | 25 | 当庭释放 |
| 参考产出、等价交换，50%胜率 | 42.5 | 3年7个月 |
| 战斗和交换均为一半，50%胜率 | 57.5 | 8年6个月 |
| 战斗和交换均为四分之一，50%胜率 | 72.5 | 14年5个月 |

刑期函数仍为 `score<=25 ? 0 : min(360,max(1,round(240×((score-25)/60)^1.4)))`，85分达到20年，20年及以上显示无期。同为无期仍按指数排序，不以多玩累计刑期。

个人页可查看五项分数、触发频次、原始战斗/交换罚分、有限减免、队友参考及原对局链接。“新旧判决对照”比较 v4 / v5，而非声明准确率提高；选出的高罚分三局和贡献缓解两局不是人工标签。守点时长、侦察、协同、防空威慑和战术牺牲未被完整记录；权重扰动范围不是置信区间，代码测试不等于模型有效性验证。

以上 v5 由历史模块函数复现，不再作为默认 API。计算模块仍为 `src/court-model.mjs` 与 `src/zhanfan.mjs`，本机登录权限与公开版只读约束不变。

#### 历史 v4：贡献与资源失衡（不再默认使用）

多账号按人局合并，仅与同局其他同队真人（包括未登记玩家）比较，均值排除本人。所有常数固定于版本，不随当前朋友名单或排名拟合。令 `clip(x)=min(1,max(0,x))`：

- 战斗达成 `B = 0.6 × clip((本人摧毁+500)/(队友人均摧毁+500)) + 0.4 × clip((本人伤害+50)/(队友人均伤害+50))`。
- 占点达成 `O = clip(本人占点/(队友人均占点+2))`。零占点不单独扣分；加 2 防止其他队友零占点时一次占点直接记满。
- 重防、实际纯空优挂载各计算 `0.8 × clip(本人该类单位击杀/(队友人均该类击杀+2))`，取较高为 `A`。同队某人该类分类未知则不用该类证据；不按部署次数推断职责，不把总战果当作击落敌机数，不叠加两种专职补偿。
- 先算战斗缺口 `D0=clip((0.8-B)/0.8)`，80% 为容忍线。取最有利的达成 `R=max(B,O,A)`，可缓解缺口 `D0-clip((0.8-R)/0.8)`，最多缓解 `D0×50%`，剩余为最终不足程度 `D`。两种辅助贡献不叠加。占点次数缺少控制时长，专职总击杀缺少战术归因，因此提供有限减刑，不一票免罪。页面有效贡献达成为 `0.8×(1-D)`，原战斗已达标则保留 B。这仍是可观察贡献代理，不是完整真实贡献。

| 维度 | 权重 | 单局罚分（0–100） |
| --- | --- | --- |
| 可见贡献不足 | 35% | `100 × D` |
| 低效战损 | 20% | `100 × max(损失-摧毁,0)/(损失+500) × D`；贡献达标时不因负交换单独加刑 |
| 蹭队友补给 | 15% | 净消耗 `N=max(从队友补给-补给队友,0)`；依赖 `S=N/max(自身消耗补给,从队友补给,1000)`；罚分 `100 × clip((S-0.35)/0.65) × D` |
| 长期胜负 | 25% | 明确胜局 0、败局 100，未知不计输；不把团队输赢完全归因给个人 |
| 友伤约束 | 5% | `100 × clip(友伤/(伤害+友伤+50)/0.05)`，不推断故意 |

- 后勤主要评估蹭饭：不送补给不扣分，送补给只抵扣同局净消耗，不额外奖励、不跨局抵账。没有超出 35% 依赖线，或不存在贡献缺口，不产生该项罚分。补给数量不与摧毁价值相加。
- 每局等权平均，个人四项以 `n/(n+10)` 向 0 收缩；胜负独立以明确胜负的 `k` 局向 50 收缩，即 `100 × (败局+5)/(k+10)`。偶发失衡会被正常场次稀释，长期反复失衡的比例更重要，不按游玩总量累计刑期。
- 原始加权罚分直接作为指数，取消 v2 的分布放大刻度。先验综合分为 12.5，但无样本仍是“待取证”，不是无罪。保留 **25 分及以下免刑**、原非线性刑期函数和 **20 年及以上无期**。不为了产生有罪者再拟合免刑线。
- 缺详情、无同队参考、非法必要字段、无效时长、队伍不明，以及全队摧毁/伤害/占点/已知专职战果都为零的无信息对局不评分。显式未知不是零；完整 protobuf 省略的标量零仍按零处理。
- 个人页展示五项罚分、失衡/补给触发次数、占点及专职战果实际缓解次数，并展示个人行为罚分最高三局、贡献缓解最大两局的原始证据和原对局链接。**这些是自动选样，不是人工标签或独立验证。** 视野、守点、激光协同、补给用途与战术牺牲仍无法完整衡量。
- 比较页差额反映同一归档在不同规则下的结果，不代表玩家突然变强；新版会排除全队无信息对局，两版评分局数可能不同。权重扰动范围不是置信区间，数据覆盖不是准确率。

历史结果由 `contextZhanfanAnalysis()`、`contextZhanfanComparison()` 复现，后者保留 v2 / v4 对照。它们不再作为默认 API 或个人判决；公开版不提供规则写接口。

#### 历史 v2 规则留档（不再默认使用）

以下为旧版 `zhanfan-v2`，用于复现对照，不是当前默认判决。v2 加入胜负维度，并用固定刻度展开长期均分。

| 维度 | 权重 | 单局依据 |
| --- | --- | --- |
| 战损交换 | 25% | `(摧毁分 - 损失分) / (摧毁分 + 损失分 + 500)` 的同队百分位，越高罚分越低 |
| 战斗 / 后勤产出 | 20% | 每分钟伤害、每分钟补给队友的同队百分位取较高值，避免仅凭低击杀惩罚后勤 |
| 占点 / 支援贡献 | 20% | 每分钟占点、每分钟补给队友的同队百分位取较高值；后勤也在此提供补偿 |
| 胜负表现 | 15% | 有效开黑局的失败率，按明确胜负的局数向 50% 收缩；胜负未知不计输，不将团队结果完全归责于个人 |
| 友伤约束 | 10% | `友伤 / (伤害 + 友伤 + 50)` 达到 5% 记本项满分，零友伤不加分 |
| 低产出补给依赖 | 10% | `max(从队友补给 - 补给队友, 0) / max(自身消耗补给, 从队友补给, 1000)`，乘以 `1 - max(产出百分位, 贡献百分位) / 100`；不将正常用补给本身视为过错 |

- 只使用合格开黑局。每局只与**同队真人**比较，含未登记玩家；注册朋友的多个账号先按人合并，同局同人分处两队不评分。观战者与负 ID 的 AI 不参与基准；至少两位有效真人才能比较。模式、地图和日期筛选先选对局，再做同局比较，不使用跨地图原始总量作为基准。
- 百分位采用含自身的中秩：`100 × (低于自身的个数 + 相同值个数 / 2) / 同队人数`，同值全队均为 50，不强行选出最差的人。前三项罚分为 `100 - 百分位`；后勤供给为零时，后勤百分位固定为 0。同局时长相同，按分钟与按总量计算的百分位数学等价。
- 缺失详情、队伍归属不明、无有效同队样本、无效时长或必要字段异常均不记零、不评分，页面分别展示排除数量。完整 protobuf 中省略的零值按零计算；显式 `null`、非数值、负数、超出安全范围的必要字段不推断为零。
- 每局等权平均，不按参战量累计加刑。用 `n / (n + 10)` 将维度均分向参考基线收缩：前三项与胜负基线 50，友伤与依赖基线 0，原始综合基线 **40 分**，换算后为指数 **50 分**。这是 10 局中性先验的启发式收缩，不是 TrueSkill 或置信概率；参考基线不等于免刑线。
- 胜负项独立使用明确胜负的 `k` 局：`罚分 = 100 × (败局数 + 5) / (k + 10)`。未知胜负不增加 `k`，没有明确胜负时保留本项 50 分先验。页面胜率为 `胜局 / k`，仅使用当前筛选下可评分的对局，可能与全部参战胜率不同。完整 protobuf 省略 `WinnerTeam=0` 属于已知的零值，负值或不对应参赛队伍的胜方视为未知。朋友多账号同局只记一次胜负。
- 原始综合罚分经固定分段刻度换算为展示指数，相邻锚点线性插值：`0→0、20→10、30→25、40→50、50→75、60→90、100→100`。中段每 1 原始分最多展开为 2.5 指数分，避免长期均分过度拥挤；全区间保持单调，不以朋友内部名次强制分配高低分。刻度不随朋友增减自动重算，也不代表证据精度提高。原始罚分保留两位小数用于核对，展示指数从未舍入的加权值换算后保留一位小数。
- **展示指数 25 分及以下免刑，显示“当庭释放”**；超线后：`刑期月数 = max(1, round(240 × ((指数 - 25) / 60)^1.4))`，封顶 360 月。35 分为 1 年 8 个月、50 分为 5 年 10 个月、70 分为 13 年 4 个月，85 分达到 20 年。**达到 20 年（240 个月）及以上显示“无期徒刑”**，同为无期仍按指数高低排名。免刑不等于没有改进空间，刑期与刻度是娱乐设计，不是实力概率。
- 无可评分样本显示“待取证”，不是零分或无罪；默认至少 **5 局可评估对局**才上榜，可调整，门槛不改变分数。不足门槛显示暂估刑期并“暂缓宣判”，少于 20 局标注“初步判决”。同分并列。权重扰动范围也使用同一非线性刑期函数。
- 个人判决和排行榜的刑期下方配有档位小字，分为：当庭释放、不足 1 年、1–3 年、3–5 年、5–10 年、10–15 年、15–20 年、无期（区间下限包含、上限不含）。例如无期显示“食堂已为你保留固定座位，出狱日期暂不排期。”暂缓宣判与待取证使用独立文案，不对证据不足的玩家直接定罪。
- “权重扰动范围”将各项权重分别乘 0.8 或 1.2、重新归一化后通过相同刻度与量刑函数计算，用于观察模型敏感性，**不是置信区间**。胜负占 15%，不独立决定个人刑期，评分涨跌不直接加刑；视野、守点时长、防空威慑、断补给和战术牺牲未被完整记录。补给指标无法识别补给是否关键；后勤在产出和贡献两项都可补偿，有利于后勤角色，但也可能高估单纯刷补给的表现。
- 方法参考：[OECD / JRC 综合指标手册](https://www.oecd.org/en/publications/handbook-on-constructing-composite-indicators-methodology-and-user-guide_9789264043466-en.html)的归一化、权重透明与敏感性分析原则；[Microsoft TrueSkill 说明](https://www.microsoft.com/en-us/research/project/trueskill-ranking-system/)中团队结果与个体不确定性的限制；[Broken Arrow 官方生存指南](https://www6.slitherine.com/news/broken-arrows-survival-guide)对后勤作用的介绍。具体公式与刑期映射均为本项目设计，不代表这些来源背书。

计算模块为 `src/zhanfan.mjs`，本机 API 与公开只读版复用同一模块；不在数据库持久化刑期，不需要迁移或重新抓取既有完整详情。以后修改规则应更新模型版本，并重新导出 / 发布只读站点。

#### 历史 v3 试算留档

`zhanfan-v3-ratio-trial` 比值草案与 `zhanfan-v3-trial2` 百分位草案保留在 `zhanfanTrialComparison()`，供历史实验复现，不是现行模型或页面默认对照。此前的三版对照均使用同批有效对局、小样本收缩；范围和标准差只是分散程度，不是预测精度或置信区间。

- 草案权重：战损交换 25%、战斗产出 20%、占点 15%、胜负 20%、友伤 6%、蹭饭行为 14%。删除独立的送补给评分，原后勤 10% 与低效依赖 4% 合并，只考虑高依赖、低贡献的蹭饭，不送补给不扣分，送补给也不直接替代战斗产出与占点。
- 比值版只替换战损交换、战斗产出、占点三项量尺。统一罚分为 `clamp(50 - 30 * log2((本人值 + b) / (参考值 + b)), 0, 100)`。交换直接比较本人摧毁分与损失分，`b=500`；战斗分别比较本人击杀价值与伤害、同局其他同队真人的人均值，平滑常数分别 500、50，两项罚分按 60% / 40% 合成；占点使用相同的队友人均参考，平滑常数 1。多账号先合并，参考均值排除本人；不使用对手。全队为零记中性 50，单次占点不直接记满贡献。常数固定于模型版本，不随当前朋友名单重新拟合。
- 重防与按实际挂载识别的空优机总击杀保留上版的同队百分位专长补偿，只对有战果者补偿，取更有利的一项、不叠加，每局最多提高 15 分贡献（战斗项最多减少 3 点原始罚分），同时限制战斗罚分在 0～100。这不是击落敌机数，也不是按部署次数减刑。
- 同队某人的单位分类或挂载缺失时，不使用对应专长的整队比较，但保留基础评分，不把未知当零。重防、空优各自独立判断是否可用；没出这些单位不额外扣分。
- 蹭饭每局计算：`净消耗 = max(从队友补给 - 补给队友, 0)`；`净依赖比例 = 净消耗 / max(自身消耗补给, 从队友补给, 1000)`。比例不超过 35%，或贡献达到同队第 60 百分位时，本项不罚。贡献取战斗产出（含专长补偿）、占点百分位的较高者。否则 `单局罚分 = 100 * ((净依赖比例 - 0.35) / 0.65) * ((60 - 贡献) / 60)`；各局等权平均，以 `n/(n+10)` 向零收缩后乘 14% 权重。35% 与第 60 百分位是试算阈值，不是官方标准。
- 为单独检验量尺变化，比值版的蹭饭证据仍使用上版百分位贡献，不改用比值分。胜率、友伤、蹭饭权重与阈值、先验收缩、免刑线和刑期曲线完全保留；不要把各分项换量尺与重设刑期同时进行。
- 同局多账号先合并再计算净消耗；供给队友只抵扣同局净消耗，不额外加分、不跨局抵账。不吃、少吃、吃但有贡献均不会因本项加刑；缺失字段仍排除，不当零。页面单独展示蹭饭罚分、净依赖超线局数、实际触发局数与场均净消耗。
- 新版中性原始罚分与旧版同为 40，完整沿用旧刻度和刑期函数。免刑线 25、20 年无期、同分并列不变；不为了拉开分差强行加刑。
- 每人可展开分项与专长补偿。分项变化是相对中性基线的原始罚分差，不是独立因果效应，不能直接相加为月数。两版都无期时显示指数变化，不把隐藏的月数当作有期刑期差。

历史实验从模块函数复现。当前 API 的 `court_compare=1` 已改为 v8 / v9 对照，省略时返回 v9；没有写入或从网页启用实验规则的接口。

#### 对局证据复核

“蘸饭刑期榜 → 案例复核”先检查指标能否识别游戏中的搭便车，而不是继续按分数分布调参。`src/court-review.mjs` 只生成事实清单，**不评分、不判刑、不伪造人工标签，不改变现行判决或既有试算**。

- 从当前筛选的完整开黑对局中找五类可复核事件：赢局中的净补给依赖、负交换但有占点、零占点但有重防或空优战果、零摧毁但供给了队友、友伤与负交换同时出现。这些是选样条件，不是有罪标准。
- 每类按对应单项量降序选取最多三位不同朋友，每人取一局；同一人局可能属于多个类别。此为定向选样，**不是随机代表性样本，不能据此估计误判率、拟合权重或验证评分有效性**。
- 多账号同局先合并；分处两队的人局不选样；机器人、观战者不作同队真人。可查看原对局、同队原始数值及本人出场型号。筛选朋友时只选该人的案例，同队证据仍完整保留。
- 补给、友伤伤害、摧毁价值分别列示，不相加成资源净成本；派兵与回收价值也不直接当作实际花费。捕获次数不能替代守点时长；出场单位不能证明真实分工；重防和空优总击杀不能当作敌机击落数。
- 缺少字段仍为未知，完整 protobuf 省略的零值按零处理。案例统一为“待人工复核”，当前人工标签数为零；不会把没有测到的守线、侦察、威慑和牺牲视为没有贡献。
- 下一步应以回放或参与者确认建立“明确蘸饭 / 正常职责 / 证据不足”的案例，再用独立、非定向挑选的对局检查误判。没有这个环节，任何曲线、权重和刑期都只能称为娱乐草案，代码测试通过不等于模型有效。

API：`GET /api/analytics/zhanfan?court_cases=1&mode=0`。本机仍需登录，公开只读版复用同一计算，不提供标签写入接口；不需要迁移或重新抓取对局。

## 朋友详细分析与专精组合

在“看守所”点击“详细分析”，或在总览 / 庭审分析中点击朋友姓名，进入该朋友的分析页。六个分页包含综合画像、专精组合、队友关系、地图表现、常用单位和最近对局。日期、地图、模式和队伍条件共同生效，默认仍为普通模式；所有统计只使用合格开黑局。

朋友表现、同队搭档，以及个人 / 总体的专精组合、地图、组合与地图交叉表、常用单位均支持点击列名排序。再次点击切换升序 / 降序，箭头显示方向；名称默认升序，多数数值默认降序，损失、阵亡和友伤默认升序。缺失数据始终排在末尾，零值和无限交换比按真实数值比较；相同值保持原有顺序。各表在当前浏览器标签页内分别记住排序，筛选、切换栏目或刷新后继续生效，点击“恢复默认”可清除。列排序不改变最佳 / 最差排行的样本门槛，同队搭档排序使用全部符合筛选的组合。

- 同一朋友多账号同局合并；分处两队时，胜负和队友关系不明确的部分不强行归类。队友表区分同局、同队和对位，并展示同队胜率、个人评分变化及对位胜率。
- 最佳 / 最差搭档按同队胜率排名，默认至少 5 局结果已知，可切换为 1、3、10、20 局。样本不足的行仍展示；胜率差只是对照，不代表因果。
- 常用单位按出场局数排序，也可按出场次数或总伤害排序；同局重复部署增加出场次数，不增加出场局数。使用率只以完整详情的参战场次为分母，“使用时胜率”是使用该单位的对局胜率。
- 被告画像首先展示“最多使用单位、伤害最高单位、击杀最多单位”。分别按部署次数、累计伤害、累计击杀比较；并列共同展示，超过三种时提示完整并列数量。只使用当前筛选内完整详情，多账号合并；没有伤害或击杀记录时不把零值列为第一名。
- 单场原始数据没有直接给出专精组合。程序使用公开卡组编辑器的单位池及 `availability.spec1/spec2` 建立专精映射，仅在出场单位对应唯一的同国两专精组合时显示“推定”。目录版本、未出场单位及转让单位可能影响结果；无法唯一识别的记录不强行分配组合。
- 管理员或账号所属朋友可在单场“团队战绩”中确认 / 修正专精组合，人工确认优先于推定，并在后续同步时保留。不同账号采用不同组合的同一朋友同局记录，整体组合暂记为未确认。只读公开版不提供修改入口。
- 总体“专精组合”“地图胜率”及“组合 × 地图”按朋友参战人次统计；同一朋友同局最多计一次。朋友分处两队时双方都会纳入，所以这里不是把整局开黑定义成一次共同胜负。

专精目录已保存于数据库。需要更新当前公开目录时，在项目目录运行 `node scripts/update-analysis-catalogue.mjs`；此操作先备份数据库，仅保存已归档单位相关的映射，不下载全部单位详情。缺少目录时分析页仍可使用，组合显示为未确认。SQLite 完整备份包含人工确认和目录。GitHub Pages / 只读导出也支持同样的分析和筛选。

本机版自动采集按北京时间（UTC+8）分时调度：白天仅在每日 06:00、12:00、18:00 各安排一轮，20:00 至次日 00:59 每 10 分钟一轮。白天只在指定时点所在的一分钟内启动；休眠、重启或其他任务占用导致错过时点时，不在其他白天时间补跑。每轮检查所有启用的账号，不再因为连续没有新对局而延长账号检查间隔，旧版保存的空闲等待时间也不再生效。没有新战报可能只是比赛尚未结束，不能据此判断账号不活跃。自动与手动同步仍遵守暂停、错误重试、请求额度及限流冷却。每次请求默认间隔至少 1.8 秒，已有任务运行时不并发采集。

法庭核心统计只使用已归档对局。账号生涯按“上次上游基准 + 其后本地已归档对局”即时推算，不按 6/24 小时重复获取。各账号固定错开为每 7、8、9 或 10 天校准一次，首次尚无基准时建立基准；校准只读取玩家页，不重扫老历史分页，也不重复获取已完成详情。必要短页核验取得的同轮玩家页可以复用，无须再发校准请求。日常本地补算场次、时长、胜负/退出、击毁损失、补给与占点；缺失详情的字段暂不补算，未归档对局由校准纠正。等级、排名、专精经验和无法可靠对应的字段保留校准值。上游基准单独保留，读取时按唯一比赛 ID 重算增量，重复导入或后补详情不会重复累计；晚导入的校准前旧比赛不再次加进生涯。界面区分本地更新时间和校准时间。已完成历史的老账号按需读取近期列表：每页 10 场，保存本页后，一旦接上上次成功更新的首页记录就停止，不必再请求一整页旧比赛。正常分页下，新增 0～9 场通常查 1 页，新增 10～19 场通常查 2 页；积累更多新比赛则继续到衔接处。停止位置只在补齐后更新，暂停、失败或本轮未补齐时保留旧位置，不能把临时导入的一场新比赛当作已接上旧档案。首次升级尚无可信停止位置时，沿用整页已归档的保守判断；上游缺页或停止位置已超出可查询范围时，可能需要更多核对。

老账号不自动重新执行历史回溯，包括旧版定期回扫遗留的游标；只有手动全量回溯重新检查旧历史。新账号仍可完成首次历史导入。每个账号独立保存游标、上游数量、失败重试时间和近期停止位置，重启后继续。首次历史导入每轮每个账号最多回溯 20 页，手动全量回溯最多 200 页；近期追赶另有 200 页的保护上限，并非固定抓取量。未完成状态与进度保留，不固定截断为 100 场。同轮近期列表和历史回溯共享已核验的分页及玩家档案；为核对短页已获取的档案也用于本轮生涯校准，避免重复请求。完整详情只补尚未完成的对局，优先满足三人条件的对局，每轮最多 50 局，其中个人其他对局最多 10 局。

“一轮”指一次同步任务：依次检查启用账号的近期列表，再统一补缺少的比赛详情和单位目录，不代表每个账号都读取历史全集，也不代表固定请求数。12 个老账号均可正常检查且无新比赛、无需补详情和目录时，通常共 12 次列表请求；部分账号处于错误冷却或命中缓存时更少。处于比赛静默的账号会跳过，实际数量可能少于 12 次。同一比赛由多个账号发现后，完整详情按比赛 ID 归档，成功后不按参与账号重复抓取。请求量应按列表分页、必要档案、未完成详情、目录补齐和重试分别相加。

**账号查询静默策略（可选，默认关闭）：** 本机“书记官室 → 查询顺序与静默”提供“启用45分钟静默与账号跳过”开关。关闭时不创建新的比赛静默，已有静默状态也不会阻止查询；原有错误冷却、请求额度和停用账号规则保留。排序与新对局即时归档不受此开关影响。开启后执行以下规则：每轮按本机已有的生涯比赛场数从高到低查询，场数缺失时使用已知历史／本地场数，不为排序额外请求。新发现的比赛立即下载并归档完整详情；查询账号和同场双方的已登记参战账号，静默至该场结束时间加 45 分钟。结束已满 45 分钟、结束时间缺失或异常的比赛不新建静默；旧比赛不会缩短已有静默。同一朋友未参战的其他账号、观战者不跟随静默。静默在私有数据库持久保存，重启、切换数据源、手动增量和全量查询都不能提前绕过；截止时刻起重新参与查询。当前账号进入静默后，后续历史分页和生涯校准延后，未完成断点保留。旧的缺失详情仍按原预算补齐，新发现的详情改为即时归档，所有请求仍受统一额度和错误冷却限制。本机“书记官室”展示查询顺序、场数和静默截止时间。

桌面管理器“后台与状态”显示今日可核实请求、已计量正文和自动同步开关。开关立即保存，可在后台未运行时修改，开启后仍需后台运行。请求统计默认从最早留存日志开始，支持起止日期、按日／月／年、所有来源／BATrace／官方上游筛选与分页；网页管理页支持同样的查询和 CSV 导出。计数分为逐次记录、旧同步日志、补充证据下限，按同步任务 ID 去重，不将新旧计数重复相加。旧轮次按开始日期归属；缺少历史响应正文计量时显示未知。现有审计补入 7,073 次同步计数和 252 次补证，共至少 7,325 次尝试；只代表已留证据的下限。导入前备份数据库，证据键防止重复导入。

本地空间页按需计算项目文件、数据目录、SQLite／WAL／SHM、备份、只读站点、缓存、程序及磁盘可用空间。按文件大小统计、跳过符号链接；备份包含在数据目录中，不能与项目总量再重复相加。正文数据量是已读取响应正文的 UTF-8 大小（解压后），不含请求、响应头和连接开销。

数据源可在桌面或本机书记官室中选择 BATrace 或官方上游直连，保存在私有数据库；切换不自动开启采集，有请求进行中时拒绝切换。官方适配使用 api.brokenarrowgame.tech 的用户、近期 ID、个人累计统计，以及 s3.brokenarrowgame.tech 的原始战报。两主机共用请求额度、串行队列与间隔；均逐次记账，403／429 冷却，不自动回退 BATrace。近期 ID 窗口不代表账号创建以来的所有历史；按需复用本地战报，新比赛原始报告只获取一次并用于完整详情。官方源支持数字游戏 ID 或 Steam64 查询，不提供昵称搜索或单位目录，目录沿用本地；官方与 BATrace 一致：省略 Type 表示默认普通模式（0），Type=1 表示自定义，Type=3 表示遭遇战。旧版误标未知的官方记录会依据已保存原始战报自动修复，原始快照保留。接口公开权限、长期保留范围和稳定性没有正式承诺；适配依据已核实响应及社区公开客户端代码，未使用合作 Token 或游戏登录凭据。

请求监控位于本机管理员“书记官室”，逐次记录数据源请求地址、用途、来源任务、开始/结束时间、HTTP 状态、失败原因与尝试次数。所有通过 SourceClient 发起的搜索、补抓、同步、目录与维护脚本均先持久记账再发送；缓存命中不计为网络请求，重试逐次计数，进程中断留下的未确认请求保守计入额度。默认最近一分钟 20 次、最近一小时 200 次、北京时间每日 1000 次，任一上限达到即阻止发送；管理员可调整，手动全量和强制刷新也不能绕过。监控失败时不会发送，自动重定向关闭以避免隐藏请求。额度与明细保存在 source_requests/source_request_blocks，重启不会清零；累计值自启用监控起计算，不冒充过去的精确请求量。管理员接口 GET /api/source/requests 支持 limit=1..200 和 before 游标读取全部记录，公开只读导出不包含监控明细。该监控覆盖本程序共享数据目录的数据源访问，不包含浏览器、其他程序或另建数据目录的访问。

目录版本及可用版本列表缓存 6 小时；指定数据库版本的完整单位资料缓存 7 天，飞机与通用挂载目录共享响应。缓存按数据源地址隔离并存入私有数据库，重启后可复用；相同响应再次取得时也会更新有效期，不受原始档案首次保存时间影响。目录脚本的 `--force` 会跳过缓存，日常运行无需强制刷新。近期首页按数据源和玩家缓存 2 分钟，手动连续检查、排队任务和重启可以共用；历史其他分页不使用跨轮缓存。短页的必要二次核验显式跳过缓存。

上游 `totalCount` 可能包含仍在历史索引中、但已不再返回比赛数据的 ID。遇到短页或空页时，程序会读取或复用本轮已获取的玩家历史索引并重复核对该页，按索引位置继续翻页，不因缺失比赛提前停止。确认缺失的 ID 单独保存，界面显示“已同步 · 历史有缺失”及数量，仅手动全量回溯时再次检查；网络错误、索引不一致仍显示同步异常。后续从其他朋友或导入档案找回比赛时，缺失标记自动解除。

出现 429 或 403 会冷却至少 1 小时，并遵守更长的 `Retry-After`；冷却按数据源保存，重启后仍有效，不绕过访问验证。网络及结构解析失败会记录到日志，保留已有数据和进度。使用“全量回溯”可以重新检查当前所有可访问历史，不会清空旧档案。

**当前数据源：** 官方适配器直接读取玩家资料、近期对局索引和原始战报；不自动回退到 BATrace。可回溯范围与详情完整度以官方当前返回的数据为准。

**历史边界：** 实测某账号生涯超过 500 场，而上游历史列表只列出 100 场。程序能保存各朋友账号历史窗口的并集，并不断积累，但无法恢复数据源已不再提供的旧记录。不能保证所有生涯比赛都能追回。对局详情也可能过期；界面分别显示汇总、完整详情和失败状态。

更早历史仍可能从其他已登记小号的记录窗口，或已有对局链接、JSON、HTML 归档中补入。没有对局 ID 或其他档案时，不会遍历全站猜测 ID。若站方提供授权的历史导出或兼容接口，可继续接入；生涯累计统计不能还原每场记录。

“书记官室 → 按 ID 补抓”支持数字对局 ID 或 BATrace 单场链接，直接尝试抓取完整详情，不依赖最近 100 场列表。成功后同样按三人条件判定；不足三人的记录只作为候选保存。链接对应的详情已过期时会提示失败，不会伪造历史。

**覆盖边界：** 已确认并实现单场及玩家相关的公开数据读取。BATrace 的社区投稿、举报、站内好友图谱鉴权和全站单位库不是本工具的采集范围。不是 BATrace 官方接口客户端，页面或内部 API 变化后可能需要更新解析器。持续长期使用应与站方确认访问频率及接口使用方式。

## 导入、导出与备份

管理员在“书记官室”导入 JSON / HTML：

- BATrace 分页对局响应 `{ "matches": [{ "matchId": "...", "data": {...} }], "totalCount": ... }`。
- `{ "matchMap": { "对局ID": {...} } }`、单条 `{ "matchId": "...", "data": {...} }` 或对应对象数组。
- 本工具导出的 `broken-arrow-court-v1` 完整档案 JSON。
- 保存的公开玩家页 HTML，或者单场 HTML（填写对局 ID）。

导入前校验所有对局，单次导入事务提交；无效文件不会留下部分结果。原始字段和未知字段完整保存，按 ID 更新去重。JSON 导入不覆盖用户和朋友归属；完整迁移使用 SQLite 备份。

主数据库为 `data/court.sqlite`，采用 WAL、外键、索引、事务和版本化初始化。`data/backups/` 每日自动保存一致性备份，保留 14 天。管理员可以随时下载一致性数据库备份或导出原始 JSON。所有不同版本的源响应以 gzip 存入 `source_snapshots`，同一内容去重，供以后重算和审计。

恢复完整备份：先用 `Stop.ps1` 停止服务，把当前 `data` 目录整体另存；把备份放入一个**新的空数据目录**并命名为 `court.sqlite`，设置 `.env` 中 `DATA_DIR` 指向该目录后重新启动。不要覆盖仍在运行的数据库，不要将旧的 `-wal`、`-shm` 文件和恢复文件混用。备份包含密码哈希和会话，按私有文件保管。

### 自动私有云备份

完整数据库与公开网页分开保存：网页继续发布到公开站点仓库，完整数据库保存到独立 **Private** GitHub 仓库的 **Releases 附件**，不反复提交大文件到 Git 历史。两项工作由同一本地后台自动运行，互不依赖；发布网页失败不阻止备份。

1. 安装 GitHub CLI，运行 `gh auth login` 完成本机登录；确保对备份仓库有写入权限。
2. 在 `.env` 配置下列项目，重启本地后台。不要在公开网页仓库填写这些配置，也不要上传 `.env`。

```dotenv
CLOUD_BACKUP_REPOSITORY=your-name/your-private-backups
CLOUD_BACKUP_INTERVAL_HOURS=24
CLOUD_BACKUP_RETENTION=14
# 如网络需要代理，可配置；不用代理则留空或删除。
# CLOUD_BACKUP_PROXY=http://127.0.0.1:7897
```

3. 后台启动后自动检查，之后每分钟检查是否到期，默认每 24 小时生成一次。电脑、后台及网络必须运行；关机不会在云端自动抓取或备份，重开后台后补做一次，不重放错过的每一轮。
4. 本地“书记官室 / 书记官室”底部的“私有云备份”可查看上次成功、大小、失败与重试时间，点击“立即云备份”可手动触发。也可在项目目录运行 `npm run backup:cloud`，或 `.\.desktop\runtime\node.exe scripts/backup-cloud.mjs`。

每次先确认仓库私有，使用 SQLite 在线备份接口获取含已提交 WAL 的一致性数据库，执行完整性与外键检查，再压缩并计算 SHA-256。先创建草稿、上传 `court.sqlite.gz` 和 `manifest.json`，核对远程附件名称和大小后才标记完成。本地 `data/cloud-backup.json` 记录成功版本和重试状态；失败保留上一份成功备份，30 分钟后重试，不会显示为备份成功。内容完全不变时可跳过重复上传。只有新备份成功后才清理超额的本程序自动备份，默认保留最近 14 份；手动备份和旧仓库文件不自动删除。上传失败的草稿保留供排查，不计作成功备份。

恢复时从对应私有 Release 下载两个附件，根据 `manifest.json` 核对压缩包和解压数据库的 SHA-256，再按上一节恢复至全新空数据目录。该备份包含用户密码哈希、会话、全部对局、原始源响应和数据库内配置；不包含 `.env`、GitHub 凭据、EXE、源码或运行状态文件。**不要把备份仓库改成公开，也不要启用 Pages。**

### 公开网页加载优化

公开网页不再先下载完整分析库才能打开：首页、普通模式 / 全部模式下的全部、近 7 / 30 / 90 天常用统计与榜单、对局列表分页，以及默认个人报告，均读取从脱敏数据库预计算的分块 JSON。个人的“其他对局”第一页也可直接查看；单场详情独立加载，专精与挂载信息不丢失。更复杂的地图、成员、同队、日期及最低局数筛选仍保留同一套算法，需要时才加载 SQL.js、WASM 和压缩后的分析库。

浏览器支持 Cache Storage 时，按快照版本缓存已访问 JSON 和分析库，重复访问可直接复用；缓存被禁用或空间不足时自动改用网络。仅保留近期版本，不缓存登录信息。清单始终从网络检查，点击网页刷新按钮切换到新快照，避免混用不同版本的数据。常用统计代表快照生成时的结果，随下一次发布更新；不会因打开网页而请求上游游戏服务器。此优化不能解决运营商到 GitHub Pages 的网络不可达问题。

## 公开版的隐私边界

公开版是独立静态网站，不需要访客连接本机后台。浏览器使用 sql.js 1.15.0（MIT）查询重新生成的只读索引，索引压缩传输，单场详情按需加载。游戏明细采用字段白名单，不等同于私有原始档案的全字段导出。

| 可以公开的生成内容 | 不会导出的私有内容 |
| --- | --- |
| 满足三人条件的对局、参赛者游戏名和游戏 ID、战绩及单位明细 | 不符合条件的候选单排记录 |
| 启用朋友的称呼、登记的游戏账号及其关联、已确认专精组合 | 本站登录名、密码哈希、会话、邀请码、确认操作人的身份 |
| 静态脚本、样式、只读索引和目录 | Steam64 字段、原始数据库、备份、原始网页、同步日志、`.env` |

**只读不等于保密。** 访客不能注册、修改账号归属、确认专精、导入或调整同步设置，但可以下载公开索引和对局明细。公开仓库的文件及历史提交也可以被下载。以后删去朋友或改成私有，不能收回别人已经下载的资料，也不会自动清除 Git 历史。

只公开 `site/` 中受管的生成文件。不要把完整项目、`data/`、数据库备份或 `.env` 上传到公开仓库。发布器会建立独立的 `site/.git`，不使用项目根目录的 Git 仓库，不执行 `git add .`，也不强制推送。

## GitHub Pages 一键部署

这里的“一键”指：完成工具安装和本人登录后，一条命令串起首次静态发布；不绕过登录、验证码或组织授权。脚本支持 GitHub.com 的独立公开仓库、`main` 分支、仓库根目录发布。

### 1. 安装工具并登录（只做一次）

安装 Node.js 24+、Git、GitHub CLI，重新打开终端后检查：

```powershell
node --version
git --version
gh --version
gh auth login --hostname github.com --git-protocol https --web
```

按 GitHub CLI 提示由本人完成浏览器授权；不要把密码、Token 发给别人，也不要放进仓库 URL。登录状态可用 `gh auth status` 检查。

### 2. 执行一键部署

**Windows 直接双击 `Deploy-GitHubPages.cmd`**，会保留终端窗口并依次询问仓库地址、公开数据确认、是否允许创建公开仓库以及是否重启本机服务。已有 `.env` 发布配置时，仓库输入直接按回车。确认问题默认均为否，输入 `y` 才同意；首次部署前仍需完成上一节的安装和登录。

不要直接双击 `.ps1`：Windows 可能仅用编辑器打开它，或报错后窗口立即关闭。双击入口使用 `.cmd`；下方 PowerShell 命令用于已经打开的终端，无需重复答题。

把下面的 `your-name` 替换成自己的 GitHub 用户名，仓库名建议保留为 `broken-arrow-court-public`。仓库应专用于生成网站，不与后台源码混用。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Deploy-GitHubPages.ps1 -Repository your-name/broken-arrow-court-public -CreatePublicRepository -AllowPublicData -RestartService
```

参数含义：

| 参数 | 含义 |
| --- | --- |
| `-Repository OWNER/NAME` | 指定发布目标；省略时使用 `.env` 已配置的 GitHub 仓库 |
| `-CreatePublicRepository` | 仓库不存在时明确允许创建**公开仓库**；已存在则复用，不重复创建 |
| `-AllowPublicData` | 明确同意公开前述朋友称呼、账号关联和游戏数据；不加就不会部署 |
| `-RestartService` | 成功后重启本机后台，加载自动发布配置；不加则需自己重启 |

本机已经配置好发布仓库时，可以直接重复执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Deploy-GitHubPages.ps1 -AllowPublicData -RestartService
```

macOS / Linux 使用同一部署逻辑：

```sh
node scripts/deploy-github-pages.mjs --repository your-name/broken-arrow-court-public --create-public-repository --allow-public-data --restart-service
```

脚本会检查登录、仓库与输出目录，重新导出只读快照，只为生成仓库设置 GitHub CLI 凭据助手，然后提交、推送并启用 Pages（`main` / `/`）。成功后保留 `.env` 中其他设置，仅更新发布相关项。重复执行不会重置数据库或朋友名单。

安全限制：不会擅自把私有仓库改为公开；不会覆盖不同远程仓库、已有其他 Pages 构建方式或不相关的非空仓库。已有发布配置指向别处时会停止，不自动改投新仓库。为另一群朋友部署应使用新的完整项目目录及独立数据库、空发布仓库，不要复制旧的 `.env`、`data/`、`site/` 后直接发布。

### 3. 确认部署成功

脚本输出 `url` 和配置结果，只代表推送、Pages 配置成功，**不是构建已经完成的保证**。进入 GitHub 仓库的 **Actions** 查看 Pages 工作流，或在 **Settings → Pages** 查看部署地址和状态。也可以运行：

```powershell
gh api repos/your-name/broken-arrow-court-public/pages/builds/latest --jq .status
```

状态为 `built` 后打开脚本返回的 HTTPS 地址，通常是 `https://your-name.github.io/broken-arrow-court-public/`。用桌面和手机分别验证首页、模式/地图筛选、朋友分析和单场详情。不要只检查首页是否返回 200。

### 不用脚本：手动配置

1. 在 GitHub 创建独立空仓库，不添加 README、许可证或 `.gitignore`。免费 Pages 使用公开仓库；GitHub Pro 等套餐可从私有仓库发布，网站本身也不因此自动私有。
2. 在本机 `.env` 中填写下节的发布设置。已有文件只修改对应项，不要整份覆盖。
3. 配好 Git HTTPS 凭据或 SSH，运行 `node scripts/publish-site.mjs` 首次推送。
4. 在仓库 **Settings → Pages → Build and deployment**，选择 **Deploy from a branch**，分支选 `main`，目录选 `/(root)`，保存。
5. 停止再启动本机后台，等待 Pages 构建完成。生成站点自带 `.nojekyll`，支持仓库子路径，无需添加前端构建命令。

参考：[GitHub Pages 发布源](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)、[套餐与可见性](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)、[GitHub Pages API](https://docs.github.com/en/rest/pages/pages)。

## Cloudflare Pages 部署

可以和 GitHub Pages 使用同一个静态仓库，也可以只选 Cloudflare。Cloudflare Git 集成支持公开或私有仓库，私有仓库不代表发布网站私有。此处没有承诺“免登录一键创建 Cloudflare 项目”：首次 GitHub 授权需要你在 Cloudflare 中完成。

1. 准备一个已推送静态文件的独立仓库。如果只用 Cloudflare 且希望仓库私有，可以先手动创建私有空仓库，再按下节配置本机发布；不要运行只支持公开仓库的一键 GitHub Pages 脚本。
2. 登录 Cloudflare，进入 **Workers & Pages → Create application → Pages → Connect to Git / Import an existing Git repository**。选择 Pages，不是 Workers，也不是手动拖放上传模式。
3. 授权 GitHub 时尽量使用 **Only select repositories**，只选择静态发布仓库，避免授权整个账号的所有仓库。
4. 选择仓库，按下表填写配置，再点击 **Save and Deploy**。

| Cloudflare 设置 | 值 |
| --- | --- |
| 项目名称 | 例如 `broken-arrow-court-public`，重名时自行换名 |
| 生产分支 | `main` |
| 框架预设 | `None` |
| 构建命令 | `exit 0`（仓库已经是构建产物） |
| 构建输出目录 | `/`（不是 `site`，因为远程仓库根目录就是导出内容） |
| 根目录（高级） | 留空 |
| 环境变量、数据库、后台地址 | 均不需要 |

5. 等部署成功，打开项目提供的 `https://项目名.pages.dev/`，检查页面和数据。下次本机向 `main` 推送新提交，Cloudflare 会自动部署。

`_headers` 为支持该文件的托管平台提供缓存和安全策略；GitHub Pages 不会应用 Cloudflare 的 `_headers` 配置。自定义域名可以在 Pages 项目中另外配置，但不能保证解决大陆网络的速度或可达性问题。

参考：[Cloudflare Git 集成](https://developers.cloudflare.com/pages/get-started/git-integration/)、[静态 HTML 部署](https://developers.cloudflare.com/pages/framework-guides/deploy-anything/)。

### EdgeOne Pages 自动部署

将 EdgeOne Pages（控制台也可能显示为 Makers）连接到现有的**独立公开网页仓库**。该仓库根目录已经包含导出的 `index.html`、`manifest.json` 和网页资源，不需要在云端连接本机数据库或再次生成快照。

1. 在 EdgeOne 创建项目，选择“导入 Git 仓库”，授权时只选择公开网页仓库。
2. 生产分支选 `main`，框架选 `Other` / 无框架，根目录为仓库根目录，输出目录为 `.`。
3. 导出的 `edgeone.json` 已设置无需安装依赖、无需构建，以及缓存和安全响应头；无需填写环境变量或后台密钥。
4. 部署后验证页面、数据和“请求更新”按钮，再绑定适合所选加速区域的自定义域名。中国大陆节点要求域名已备案；默认域名的访问与预览时效限制以控制台为准。

本机每次将新网页推送到这个仓库后，EdgeOne 会自动部署。GitHub Pages 可以同时保留，两者各自部署同一份网页文件。`edgeone.json` 对首页和数据版本清单禁用边缘缓存，对带内容摘要的资源启用长期缓存，避免更新时继续读取旧版本清单。

参考：[EdgeOne 配置文件](https://edgeone.cloud.tencent.com/pages/document/162936771610066944)、[部署指南](https://edgeone.cloud.tencent.com/pages/document/162936814287618048)、[域名说明](https://edgeone.cloud.tencent.com/pages/document/175191784523485184)。

## 日常更新与手动发布

网页发布完成以 GitHub Pages 对应提交构建成功、且公开地址 manifest.json 的版本与本次导出一致为准。推送成功后显示“等待部署”，构建失败或 60 秒无进展时最多自动重新触发一次；5 分钟内无法确认上线则显示失败并保留重试状态，自动等待 15 分钟后重试，手动更新可立即重试。重启后继续验证已推送版本，未确认部署时群友更新请求不会回报完成。GitLab 等其他托管目标只报告已提交，不冒充部署成功。部署检查使用已登录的 GitHub CLI 和 curl，沿用已配置代理。


### 自动更新

在本机 `.env` 设置以下发布项，随后重启后台：

```dotenv
STATIC_EXPORT_ENABLED=1
STATIC_OUTPUT_DIR=./site
PUBLISH_GIT_REMOTE=https://github.com/your-name/broken-arrow-court-public.git
PUBLISH_GIT_BRANCH=main
PUBLISH_MIN_INTERVAL_MINUTES=120
```

发布版每天在 02:00–03:00、14:00–15:00 各随机采集一次；本机版采集按北京时间白天每日 06:00、12:00、18:00，晚间 20:00 至次日 00:59 每 10 分钟执行。每轮采集及详情补全结束后立即检查发布，有公开内容变化就生成并推送新版本，不再等 120 分钟；排队中的采集会先完成，自动导出不会在采集进行中启动。手动导入、改名、账号归属及专精更正等公开数据修改成功后也立即检查发布；若采集或发布正在运行则合并排队，完成后继续。后台脚本等外部写入由每分钟的补充检查发现，数据变化不受 120 分钟间隔限制；失败重试等待仍保留，重启后继续检查尚未推送的数据。没有新版本就不会制造空提交或无效构建。仅界面代码等文件变化仍按 `PUBLISH_MIN_INTERVAL_MINUTES` 合并推送，默认 120 分钟。推送失败后自动等待 15 分钟再试，手动“立即更新网页”可主动重试。托管平台随后还需要完成部署，因此采集结束不等于网页瞬间更新。请求失败、限流、电脑休眠或后台未运行会延迟更新，不是定时送达保证。本机网页侧栏和桌面管理器显示上次同步结束距今多久及完成、部分完成或失败状态，与网页发布时间分别显示。

没有设置 `PUBLISH_GIT_REMOTE` 时只本地导出，不推送远程。自动推送失败后至少等待 15 分钟再试。`.env`、GitHub 登录凭据、SSH 私钥都只留在后台机器上，不需要填写到 Pages 环境变量。

### 立即发布最新数据

**Windows 双击 `Publish.cmd` 即可立即发布**，窗口会保留，显示导出、推送进度与最终结果。它使用现有 `.env`，不会重新建仓库或更改 Pages 设置；首次部署未配置成功时会明确报错。

终端方式：

```powershell
node scripts/publish-site.mjs
```

或者使用 Windows 包装脚本：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Publish.ps1
```

手动命令会重新导出快照，跳过自动发布的间隔与失败退避等待，提交需要发布的改动并推送；仍然遵守互斥锁、远程仓库检查和不强推规则。如果内容与已发布版本完全相同，不会生成新提交，因此也不一定触发新的云端构建。`changed: false` 只说明本次导出内容没变，不等于推送失败；查看最终错误、GitHub 提交和部署状态。

### 更新功能或样式

1. 更新完整项目中的源码，保留 `.env`、`data/` 和独立的 `site/.git`。不要把只读站点仓库拉取到后台目录覆盖源码。
2. 修改后先验证本机程序；更新前推荐下载一致性数据库备份。
3. 停止再启动后台，加载新的服务端代码；运行手动发布命令导出并推送新前端和数据。
4. 等云端构建成功，访问正式域名并刷新。只刷新浏览器不会触发采集、推送或云端重新部署。

- 本机：`node scripts/service.mjs status`；书记官室中查看同步及“只读发布”事件。日志在实际 `DATA_DIR` 下的 `server.log`、`server-error.log`；私有发布状态是 `publication.json`。

保留最近两代本地静态资源；老页面遇到过期资源时需要重新加载。页面每分钟检测新版本并提示刷新。后台浏览器不必保持打开，但机器和服务需要保持运行、联网；休眠期间不会采集或上传。仅界面代码等文件变化默认两小时合并以减少部署次数，不等于承诺任何云平台的免费额度足够，实际额度以平台当前规则为准。

## 常见部署问题

| 现象 | 排查与处理 |
| --- | --- |
| 手机打不开 `127.0.0.1` / `localhost` | 这会指向手机自身。公网只读版用 `github.io` / `pages.dev` 地址；同一 Wi-Fi 下访问后台需另外配置局域网监听 |
| 电脑能开，手机免代理打不开公网地址 | 换 Wi-Fi/移动数据对比，记录具体域名、报错和运营商。Pages 托管不保证大陆直连，自定义域名也不保证；不要反复改程序来处理网络超时 |
| 部署成功但页面一直加载 | 检查 `manifest.json`、`.sqlite.gz`、`.wasm`、`.mjs` 是否可下载以及浏览器是否支持 WebAssembly 和 gzip 解压 API；手机更新到现代浏览器；首次需下载索引，不只是 HTML |
| 首页 404 或只有空白 | 确认 `main` 已推送、发布目录是远程仓库根目录 `/`、根目录有 `index.html`、构建已成功；Cloudflare 确认创建的是 Pages |
| 图表显示 0 局 | 先在本机完成同步，确认三位不同朋友确实参战；默认普通模式、日期和同队筛选也可能排除记录 |
| `gh` / `git` / `node` 不是命令 | 安装对应工具并重新打开终端；应用需要 Node.js 24+ |
| 双击后没反应、打开编辑器或窗口闪退 | 使用 `Deploy-GitHubPages.cmd` / `Publish.cmd`，不要双击 `.ps1`。启动器保留窗口；查看进度、错误或是否正在等待输入。部署确认输入 `y` 后才能继续 |
| CLI 已登录但推送失败 | 检查 `gh auth status`、仓库写权限、网络与凭据；一键脚本只在生成仓库内接入 CLI 凭据，不修改全局 Git 设置 |
| 一键脚本拒绝私有仓库 | 属于安全限制，不会自动公开资料。使用新的公开空仓库，或在支持私有来源的 Pages 套餐中手动配置 |
| 输出目录非空、不受管文件、远程不匹配或已有暂存修改 | 不要删除数据库、强推或对项目根目录 `git add .`。先核对 `site/` 及其 origin，处理不相关修改；不确定时保留旧目录并选择新的独立输出目录 |
| `已有静态导出或提交任务正在运行` | 等正在执行的任务结束后重试。不要在任务运行时强删锁或移动 `site/` |
| 线上还是旧数据 | 对比本机导出版本、仓库最新提交、云端当前部署提交；三者不同就逐段检查。确认部署完成后重新加载页面 |

出错时不要贴出 `.env`、数据库、完整原始日志、Token、Cookie 或 Deploy Hook；提供脱敏后的错误信息、提交号、页面截图及公开网址即可。

## 配置与局域网

将 `.env.example` 复制为 `.env` 后修改。持续同步开关和请求间隔可以在界面调整，自动采集频率固定采用北京时间分时策略，不再使用旧的单一 `sync_minutes` 设置。判刑统计窗口至少 30 天：刑期榜和个人判决移除近 7 天选项，自定义不足 30 天时不生成刑期；普通战绩查询仍可筛选近 7 天。“全部”不要求注册满 30 天，已有最低可评估局数门槛不变。`DATA_DIR` 为相对工作目录或绝对路径。`SOURCE_BASE_URL` 可切换到站方授权提供的兼容数据源。`SOURCE_DETAIL_PATH` 仅在站方提供了兼容 JSON 详情端点时设置，默认从已验证的公开单场页面读取。

| 配置项 | 用途 |
| --- | --- |
| `HOST` / `PORT` | 后台监听地址与首选端口，默认 `127.0.0.1:4317` |
| `DATA_DIR` | 私有数据库、备份、日志和服务状态目录，默认 `./data` |
| `SOURCE_BASE_URL` | 授权的兼容采集源，默认 BAtrace |
| `STATIC_EXPORT_ENABLED` / `STATIC_OUTPUT_DIR` | 是否自动生成公开快照，以及独立输出目录 |
| `PUBLISH_GIT_REMOTE` / `PUBLISH_GIT_BRANCH` | 独立静态发布仓库及分支；未配置 remote 时不推送 |
| `PUBLISH_MIN_INTERVAL_MINUTES` | 仅界面代码等文件变化的自动推送最小间隔，默认 120 分钟，下限 5 分钟；采集、导入和其他公开数据变化不受此限制，失败重试间隔仍保留 |
| `PUBLIC_ORIGIN` / `SECURE_COOKIE` | 仅在后台本身放到 HTTPS 反向代理后时配置，不要填写 GitHub Pages 地址 |

默认只监听本机。朋友需要从其他电脑注册时，可以在 `.env` 设置 `HOST=0.0.0.0`，重启后用此电脑的局域网 IP 访问，且须允许 Windows 防火墙的对应端口。应用不自动修改防火墙或路由器。不要为静态只读展示开放电脑公网管理端口；确需公网管理后台时，应另外配置 HTTPS 反向代理、访问限制及相应 Cookie/Origin 设置。

登录使用 scrypt 密码哈希、HttpOnly/SameSite 会话 Cookie、CSRF 及来源检查、邀请注册、管理权限和登录限速。停用朋友或更新密码会撤销会话；管理员的配置、注册、归属调整和导入等操作有审计记录。

- “单位详细数据”可用加减按钮在 60%～160% 间独立缩放，点击百分比还原；手机双指缩放只影响该区域，单指继续横向或纵向滚动，桌面保留鼠标拖动。
- 挂载变体按已归档游戏目录的 `ThumbnailOverride`、`ReplaceUnitId` 与本局实际 `OptionIds` 匹配；未知选项、同槽冲突或多个不同覆盖图标时保留基础图标，变体图片加载失败也会回退。运行 `node scripts/cache-unit-icons.mjs` 从现有固定版本游戏快照重建映射并补齐图片，`--offline` 只更新目录和报告缺图；模型保存于 `analysis_catalogue.unit_icon_variants`，公开版仅带已选图标名与图片。

### 对局价格版本

对局列表和详情标签展示游戏版本。战报不包含原始版本号，目前依据[官方正式服公告](https://steamcommunity.com/app/1604270/allnews/)的时间表标注 2026 年 7 月以来的版本，具体规则在 `public/match-version.js`；维护期间、未提供具体热更时间的更新当天或时间缺失时显示“版本待确认”。这是按正式服时间推算的展示标签，不把价格目录名冒充游戏补丁版本，也不改变历史价格计算；后续正式版本发布需更新此时间表。

团队战绩展示按伤害选择的两项高光：“高光单位”取单次部署伤害最高的实例，保留实际挂载名称和图标；“高光兵牌”取同一单位 ID 全部部署的总伤害最高者，不同挂载按原始单位 ID 合计，列出本局实际详细型号；同一 ID 对应多个名称时去重并列，不把合计战果误归给某一个挂载。进入玩家详情展示单位伤害最高、兵牌伤害最高、单位击杀最多、兵牌击杀最多四项。兵牌高光可进入总计页，再查看各实际挂载及实例记录。单位卡片并列显示阵亡和退款数，零值也显示。全零或无有效数据时不虚选冠军。单位详情的返回入口为有边框的按钮。兵牌区仅保留横向拖动，隐藏独立滚动条；纵向使用整个详情页的滚动，单独缩放仍可用。

团队战绩同时显示敌我双方的卡组；无法唯一识别时显示“专精组合未确认”，不填猜测结果。压缩行距并省略过长的玩家名、卡组名与高光名称，悬停可查看完整名称。原始字段、原始档案页签和下载入口只提供给本地后台管理员，公开网页及非管理员视图均不显示；这只控制界面入口，正常统计仍使用白名单内的战报数据。

团队战绩的玩家名下与玩家本局详情展示原始 `Medals` 数组中实际授予的奖章，敌我双方均显示。编号及图片文件按 BATrace 公开奖章目录映射，中英文名称沿用游戏本地化原名，悬停可查看中英文名称；未知编号显示通用奖章，图片缺失保留占位图标。30 张图标来自同一公开 BATrace-IMG 图库，经 Git blob SHA-1 校验后缓存并缩为 64×64 PNG，总计约 190 KB，随网页和桌面程序一起提供。重建：先运行 `node scripts/cache-medal-icons.mjs`，再运行 `scripts/resize-medal-icons.ps1`。

个人画像和常用单位保留基础型号总计，存在挂载改名时可展开“名称变体”明细。变体按原始型号 ID + 对应对局实际名称分组，同名的不同挂载合并；单局同一朋友的多个账号、多个同名挂载只记一次参战人次，部署次数、伤害及击杀仍逐个实例累计。变体参战人次可重叠，不能相加当作型号场次。公开索引保存已经按版本解析的名称，不在访客端拿最新挂载目录重算旧局名称。

价格按对局开始/结束时间选择 `unit_loadout_history.price_catalogues` 中独立保存的目录，不按数据导入时间或最新目录重新计算。目录更新前会归档旧目录；同一挂载 ID 在不同版本可以有不同价格。公开站点保存每局已经解析的价格，与本地一致。

`node scripts/install-price-versions.mjs` 会先备份数据库，再冻结现有 1.2.0_od 价格，并建立 1.2.1 的官方调价校正目录。切换参考官方公告的 2026-10-20 13:00 CEST（北京时间 19:00）部署维护开始时间；横跨维护、时间缺失或版本区间重叠的对局不猜价格。更新前快照保留当时目录口径，不能据此证明更早历史补丁的准确价格。

公告校正保留旧价校验及修改记录，避免重复套用差价；完整游戏原表优先于公告推导。现已从本机正式构建 26052592 核实 542 条单位记录、617 个挂载槽和 2051 个挂载选项，包含此前待确认的 8 种单位。原表能区分相同 ID 被改名、改价的挂载；例如 A-10C 的 2056 从空挂载变为 4x MK84，不能沿用 0 分。原表与公告存在差异时按本局游戏版本的原表计价，例如工程兵 6 人编制实际为 55 分。

`node scripts/import-game-prices.mjs --directory=<已提取目录> --dry-run` 先验证原表指纹、唯一 ID、关联槽位和完整性；去掉 `--dry-run` 后先备份再导入，保存完整差异报告到 `data/price-audits/`，且不会修改游戏安装文件或旧版价格快照。输入目录需有含资源指纹、逐表指纹和构建号的 `manifest.json` 及 `tables/{Units,Modifications,Options}.json`。本机新版战报 3 场、30 名玩家的部署总分已与原表逐一完全核对。

目录版本每 6 小时检查一次，仍遵守同步暂停和上游冷却；已核实的游戏原表不会被迟到的上游旧目录覆盖。未来版本必须有独立生效区间，不能覆盖旧区间。未知挂载不从其他补丁借价格。价格来源和版本可在兵牌提示及单位详情查看。

`node scripts/complete-game-catalogue.mjs --directory=<相同原始表目录> [--dry-run]` 补齐其他页面的目录：核对 8 张表的构建和指纹，生成 542 条基础单位展示记录，以及 52 条固定翼挂载判定记录。个人画像、常用单位和单位统计按基础型号累计，名称使用统一的当前基础名；单局名称和价格继续保留对应版本。空优榜独立冻结旧版 51 条飞机目录，并按每局时间选择新旧武器表，不会将新版炸弹挂载沿用为旧版空挂载；无法确认版本时不猜判定。公开只读版导出相同的安全字段与版本判定目录。
